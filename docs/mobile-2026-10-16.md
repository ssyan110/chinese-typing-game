# Mobile layout and input

The battle now has a dedicated phone/tablet layout. The same spell buttons and live feedback move next to the field and input, retaining their original event handlers, IDs and accessibility names. Rotating or widening the window restores the original desktop sidebar without restarting the duel or duplicating controls. Small portrait screens use a compact battle header; landscape places the field beside the controls. Safe-area padding accommodates cutouts and home indicators.

The field height is fitted after measuring the actual spell deck and input/keyboard. Space is reserved for combat feedback so successful answers do not push the input down. Zhuyin keys remain visible with the active target; other touch controls have larger labels and tap areas. Touch devices do not run the enemy's continuous idle animation. Inputs have a minimum 16px type size, with autocorrect/capitalization disabled for Chinese entry; pinch zoom remains enabled.

Hanzi typing follows the visual viewport when the software keyboard changes its height or pans the visible page. The compact typing frame keeps the real arena target, HP, spells, pause and input above the keyboard; it does not add a duplicate question box. Keyboard dismissal restores the regular layout. Large touch tablets up to 1400 CSS pixels receive the same keyboard adaptation. When less than 280px remains above a keyboard, optional spell choices and artwork temporarily give way to HP, the target, countdown, pause and input; dismissing the keyboard restores them. Desktop layouts above 1024px with a fine pointer retain their existing behavior.

The implementation follows the distinction between layout and visual viewports described in [Chrome's keyboard viewport documentation](https://developer.chrome.com/blog/viewport-resize-behavior/) and the [VisualViewport API documentation](https://developer.mozilla.org/en-US/docs/Web/API/VisualViewport). The viewport meta hint is supplementary; the visual-viewport listener also handles browsers that do not resize their layout viewport.

## Verification

- 28 Node tests: the existing engine, complete vocabulary coverage, persistence and entry checks, plus keyboard shrink detection, normal browser-chrome changes, pinch zoom, landscape and large touch-tablet detection.
- `scripts/browser-mobile-check.js`: 280 assertions across three modes and ten device sizes, using Chromium mobile contexts with real touch events. Sizes: 320×568, 375×667, 390×844, 430×932, 768×1024, 1366×1024, 568×320, 667×375, 844×390 and 915×412. Checks include successful input, no unintended errors, minimum Zhuyin key widths, target/input visibility, pause, no horizontal overflow and restoring desktop controls without losing progress.
- A separate visual-viewport fixture shrinks the visible height to 420, 360, 300, 240, 200 and 180px with a 35px pan. It checks the target and input remain visible, zoom is not misidentified as a keyboard, and keyboard dismissal restores the layout.
- `scripts/browser-mobile-campaign.js`: all three modes complete a full 20-item chapter at 320×568 using touch events, including three reward selections, the optional 20-row vocabulary result and persisted completion after reload.
- Existing curriculum, defeat/retry, IME composition-event, audio, accessibility, endless and desktop-fit regressions are retained. Long Zhuyin tests use the actual 15-symbol HSK 成群結隊 target and check actor/target and status/countdown separation in both orientations.

Evidence is retained in ignored `output/mobile-*.log` and `output/playwright/mobile-*.png`. Browser touch emulation and controlled visual-viewport/composition events are not physical iOS/Android keyboard or Safari acceptance. No connected physical phone was used; actual native IME candidate-window behavior still requires device testing.
